## Classify the DataMan Requirements

You practiced requirement triage with generic software statements. Now apply the same reasoning to DataMan. Classify each statement based on what it communicates **right now**, not what you think the writer probably meant.

Outcome

**MLO 2.1 → CLO 2:** Distinguish functional from non-functional requirements using evidence from the DataMan case.

### Your four categories

Functional Requirement

Describes required system behavior or a capability the system must provide.

Non-Functional Requirement

Describes a quality, constraint, or operating condition on how a capability must work.

Not Ready

Points toward a possible need, but is still too vague, incomplete, or untestable.

Proposed Solution

Specifies an implementation or design choice instead of stating the underlying need.

Analyst rule

**Classify the statement you have, not the requirement you wish it were.** A reasonable idea can still be too vague or too solution-specific to count as a defensible requirement.

### How to complete the quiz

1. Read all 18 statements.
2. Sort each statement into the category that best describes it.
3. Submit your attempt.
4. Review the feedback for any statements you misplaced.
5. Retry as needed until you can explain the distinction, not just recognize the wording.

Caution

A statement appearing in this quiz does not automatically make it an approved DataMan requirement. This activity asks you to classify the statement first. Evidence and elicitation determine whether it belongs in the project later.

### What comes next

After this classification check, you will move into requirements elicitation and begin asking a harder question: **What evidence do we still need before a stakeholder request can become defensible project work?**
