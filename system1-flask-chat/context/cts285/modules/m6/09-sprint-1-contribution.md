CTS-285 · Module 6 · Graded Evidence

## Sprint 1 Contribution

Submit the GitHub evidence for the product slice you personally contributed to Sprint 1. The pod shares an increment; this grade reads only evidence attributable to you.

Outcome

**MLO 6.1 and MLO 6.3 → CLO 4, CLO 5:** convert acceptance criteria into executable evidence and deliver a bounded increment against an explicit Definition of Done.

### Submit one GitHub link in Canvas

Submit the pull request, branch comparison, or stable repository location that makes your own contribution easiest to inspect. Do **not** upload duplicate code files to Canvas.

### Your evidence must make these three things visible

1. **Your implementation contribution.** The commits or pull-request changes must show work attributable to you and traceable to the sprint scope.
2. **Your executable test evidence.** At least one acceptance criterion for your contribution is represented by a test with a visible fail-first → implementation → pass sequence, or equivalent Git history that demonstrates the test could detect the missing behavior.
3. **Your Definition-of-Done accounting.** Your slice is checked against `docs/definition-of-done.md`, including any not-met result and its classification. A clean pass is acceptable; an unchecked pass is not.

What is not graded here

Your teammate’s output, the size of the pod’s total increment, commit count by itself, or whether every Definition-of-Done line passed.

### Pre-flight

- the submitted link opens to the intended evidence;
- your own commits are identifiable;
- the relevant acceptance criterion can be located;
- the test can be run from the repository instructions;
- the Definition-of-Done result for your slice is present and honest.

How this is graded

**10 points:** implementation evidence 3, executable-test evidence 4, Definition-of-Done accounting 3.
