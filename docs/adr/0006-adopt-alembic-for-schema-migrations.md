# ADR-0006: Adopt Alembic, and rebuild on Render Pro rather than migrating

- **Status:** Proposed
- **Date:** 2026-07-29
- **Deciders:** norrisaftcc (product), Claude Code (implementation)
- **Supersedes:** KEEP entry K6

## Context

K6 was frozen three days ago:

> **No schema change to an existing table until Alembic lands.** `db.create_all()`
> creates missing tables and does nothing else. A new table is free on the next
> deploy. A new column on an existing table silently does nothing and then raises
> `UndefinedColumn` in production — on a service that auto-deploys from `main`.
> Tests cannot catch it: they run on in-memory SQLite, which builds the schema
> fresh every run.

That entry is the reason ADR-0004 is designed as three *new* tables rather than
columns on `Conversation` and `Message`. It bought one safe schema change, and
said so.

Two things have since changed.

**Render is now Pro tier.** The free plan's one-Postgres-per-workspace limit and
30-day rolling expiry are gone. A second database — for rehearsal, for staging —
is now possible, and a database that does not expire is a precondition for
graded transcripts existing at all.

**We are rebuilding on new Render resources rather than migrating the old ones.**
The course lead's call, and it removes the hardest part of adopting Alembic.

That second point deserves spelling out, because it is the whole reason this ADR
is short. Introducing Alembic to a database that `create_all()` built is the
awkward case: the tables exist, no `alembic_version` row exists, and the first
`upgrade` therefore tries to create tables that are already there and fails. The
fix is a one-time `flask db stamp head` run by hand against production — a manual
step, done once, that nothing verifies and that silently corrupts the migration
history if done at the wrong revision.

A new database has none of that. It starts empty, `flask db upgrade` builds the
schema from the baseline revision, and Alembic owns it from the first row. The
riskiest step in the whole plan disappears by not needing to exist.

The old free-tier database is written off. It was provisioned around 2026-05-17
against a 30-day expiry, so it has most likely lapsed already; it held demo
traffic and a finished CSC 114 pilot, and K12's export question closes as moot
along with it.

## Decision

### 1. Alembic, via Flask-Migrate

`flask-migrate==4.1.0` in `system1-flask-chat/requirements.txt` as a **runtime**
dependency, not a dev one — `flask db upgrade` runs on the server.

`migrations/` holds one baseline revision describing `groups`, `conversations`
and `messages` exactly as `create_all()` left them. It was autogenerated against
an empty database and deliberately not hand-edited: it should be precisely what
the models declare, so any difference between the two is a bug in one of them.

### 2. `create_all()` is gated on `TESTING`

The two mechanisms must never both run against a real database. `create_all()`
builds whatever the models declare and writes no `alembic_version` row, so a
table it creates is invisible to Alembic — the next migration tries to create it
again and the deploy fails on a table that already exists.

It stays for tests, because the suite depends on it: the `app` fixture in
`tests/conftest.py` never calls `create_all` itself, so every route test would
run against an empty database without it. Running migrations per test would be
more faithful and much slower, for a schema `test_migrations.py` already checks
directly.

### 3. Migrations are applied as a pre-deploy step

`preDeployCommand: flask db upgrade` in `render.yaml`, which runs before the new
version takes traffic. Pre-deploy commands are a paid-plan feature, so this is
itself something Pro tier unlocked.

### 4. Drift is a test failure, not a production failure

`system1-flask-chat/tests/test_migrations.py` applies the migrations to a real
file-backed database and compares the result to `db.metadata` via Alembic's own
`compare_metadata`. A model changed without a migration fails CI.

**This is what replaces K6.** The prohibition existed because nothing could
*detect* the mistake — the model is the only thing the SQLite suite builds from,
so a missing migration was invisible until production. Verified by adding a
column to `Group` and confirming the test fails, then reverting; a guard that has
never been seen to fail is not a guard.

The file also asserts the reverse of §2 in both directions: `create_all` does not
run when `TESTING` is false, and does when it is true.

### 5. Staging is for rehearsing migrations, not for parity

A second Postgres, `teacherbot-pro-db-staging`. Its job is narrow and worth stating
so it does not drift into being a half-maintained clone of production: a
migration is applied there first, and only then to `main`.

This matters because the test suite runs on SQLite. SQLite will accept things
Postgres rejects — type changes, constraint additions against existing data,
anything involving a non-null column on a populated table. `test_migrations.py`
proves a migration matches the models; only a Postgres run proves it survives
contact with real data.

## Consequences

**Easier.** ADR-0004 stops being a one-shot design. It can still ship as new
tables — that remains the cleaner shape — but a follow-up column on `Exchange` or
`Turn` is now an ordinary migration rather than an outage. Given the assessable
unit is the freeze event and that design will move as the gradebook takes shape,
this matters more than it sounds.

**Harder.** Every model change now needs a migration generated and reviewed, and
a forgotten one is a red build. That is the trade being made deliberately: a
visible failure in CI instead of an invisible one in production.

**New failure mode, named.** `preDeployCommand` failing blocks the deploy. That
is correct behaviour — a half-migrated database serving traffic is worse — but it
means a bad migration takes the deploy down rather than the schema, and the fix
is a rollback of the migration, not of the service.

**Still not covered.** The suite runs on SQLite, so it cannot catch a
Postgres-specific migration failure. §5 is the mitigation and it is a process,
not a test. Worth revisiting if the schema starts changing often.

## Alternatives Considered

**Migrate the existing free-tier database.** Keeps the pilot data and the service
URL. Rejected because it requires the hand-run `flask db stamp head` described
above — an unverifiable one-time manual step against production, to preserve a
database that has probably already expired and holds demo traffic plus a finished
pilot.

**Keep `create_all()` and stay new-tables-only.** Zero new dependencies, and it
is what ADR-0004 was written against. Rejected because it does not survive
contact with a gradebook: the first time a graded field needs to change type or
gain a constraint, there is no path that does not involve downtime and hand-written
SQL against student data.

**Alembic directly, without Flask-Migrate.** One fewer dependency and full control
of `env.py`. Rejected as a worse trade — Flask-Migrate is a thin wrapper that
already knows how to find the app's engine and metadata, and hand-rolling that
wiring is the part most likely to be subtly wrong.
